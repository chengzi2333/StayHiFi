# StayHiFi：播放触发的实际传输诊断设计

- 日期：2026-10-30
- 状态：builder-check 已完成；用户已批准完整方案，进入实施计划；不加任何设置项、开关、弹窗或新入口
- 关联证据：`~/Documents/stayhifi用户反馈/1.2.2/logSchemaVersio.txt`、`~/Documents/stayhifi用户反馈/1.2.2/日志.txt`
- 既有边界：`docs/superpowers/specs/2026-10-25-lhdc-quality-realtime-diagnostics-design.md`

## 1. 背景与真实问题

当前“实际传输”只读取 `dumpsys bluetooth_manager` 的 `A2DP <codec> State:` 与 `transmission bitrate`。最新外部样本中：

1. Xiaomi 15 Pro：设置写入与读回成功，播放中仍为 `no-section`，现有线索未见 LHDC quality/bitrate。
2. 一加 Ace 5：设置写入与读回成功，`isMusicActive=true` 时有 LHDC V5 段但 `no-bitrate`。

这些样本证明当前路径拿不到可证明的空中码率，但现有过滤日志不足以判断：系统完全没有字段，还是 App 过滤/解析遗漏。作者没有这些真机，因此下一轮反馈必须自动留下更完整、仍受隐私与体积约束的证据。

用户同时提出实际输入/输出采样率。音频源、系统混音、A2DP 编码器和耳机 DAC 是不同层，不能用同一个“实际采样率”名称冒充。

## 2. 用户已确认的交互裁决

1. **不新增采集按钮**，也不把采集塞进“复制反馈日志”。
2. 识别到音乐播放后自动采集；为了覆盖链路稳定前后的状态，使用短窗口内多次采样，随后自动停止。
3. **复制反馈日志只负责导出**，不得新增 dumpsys、provider bind、Root/授权交互或等待。
4. **同一 MAC + 完整 CodecConfig + provider generation 在每个 App 进程最多采集一个窗口**；暂停/换歌不重复。只有换机、完整配置变化或 provider 代次变化才允许新窗口；用户清空日志后允许按新会话重采。
5. 0/3/8 秒仅用于发现状态变化，不保存三份原文；字段去重、变化合并，诊断只占少量行，整份反馈仍最多 200 行。
6. 本轮首页不增加输入/输出采样率字段；先把来源明确的值留在诊断证据中。
7. 日志上传平台选择仍处于待定，本功能只做本地日志，不联网、不上传。

## 3. 目标

1. 在 App 进程存活且系统提供播放信号时，自动捕获当前播放相关的有界诊断窗口。
2. 覆盖蓝牙编码器段、`dumpsys audio`、`dumpsys media.audio_flinger` 三类独立数据源。
3. 保留每个来源的原始相关片段、时间、连接/配置上下文和独立失败状态，使外部日志能区分“无字段 / 被过滤 / 权限或超时 / 状态变化”。
4. 复制时无需系统 I/O，暂停音乐后仍能导出此前证据。
5. 防止连续播放回调、配置抖动、清空日志或换机造成重复采集、日志爆炸或旧结果写回。
6. 保持现有首页、实际传输四态、写入/读回和 Root/Shizuku 授权语义不变。

## 4. 非目标与反目标

- 不声称让 Xiaomi、一加或所有机型立即显示实际码率/采样率。
- 不从 cs1、采样率、位深、PCM 增量或理论压缩率推算实际空中码率。
- 不把 `isMusicActive=true` 单独当成声音一定走目标 A2DP 设备的证明。
- 不把 `AudioManager.PROPERTY_OUTPUT_SAMPLE_RATE`、设备支持采样率列表或推荐 fast-path 值当成当前蓝牙实际采样率。
- 不读取其他 App 的 AudioTrack，不采集音频内容、媒体标题、麦克风或 HCI snoop。
- 不新增常驻轮询服务，不增加开机任务，不在整个播放期间无限 dumpsys。
- 不改变 `BtStateParser` 的现有匹配规则来猜其他段，不修改自动/手动写入目标。
- 不在本轮展示“实际输入采样率 / 实际输出采样率”首页字段。
- 不把原始完整 dumpsys 无筛选写入 LogStore、剪贴板或网络。

## 5. 采样率语义边界

| 层 | 可获得性 | 允许的事实表述 |
|---|---|---|
| 音乐 App / 源 AudioTrack | StayHiFi 通常不能直接读取其他 App 的 AudioTrack | 不宣称已知 |
| Android 播放轨 / 混音线程 | 可能出现在 audio/audio_flinger 诊断中，需样本验证 | “系统播放轨/混音诊断值”，不等于蓝牙实况 |
| A2DP 当前协商配置 | 已由 `BluetoothCodecConfig` 读回 | “A2DP 协商采样率”，不是源或 DAC |
| 实际空中传输采样率 | 需要厂商栈运行时证据，当前样本未证明 | 无证据时不可用 |
| 耳机 DAC / 最终发声 | 手机一般无法读取 | 不展示、不推测 |

后续若做首页展示，必须按来源分别命名；本轮不决定展示。

## 6. 方案结构

### 6.1 进程级播放诊断控制器

新增单一 `PlaybackDiagnosticsController`，由 Application 在 provider coordinator 初始化后创建并持有。主触发采用 `AudioManager.AudioPlaybackCallback`；回调内只做轻量状态判断并投递到注入的后台 dispatcher，禁止在主线程执行 dumpsys/provider I/O。

- 以 `AudioManager.isMusicActive` 和当前本机 A2DP 连接事实共同门控；播放回调本身不证明输出目标。
- 无回调或厂商不投递时，只复用现有事件点的 `isMusicActive` 检查作为补充信号，并进入同一控制器和去重状态机；**不为诊断新增常驻或定时轮询**。因此无法保证“进程存活但始终收不到播放/连接事件”的 ROM 一定能触发，必须在日志中保留覆盖边界。
- App 进程死亡即停止；不承诺进程不存在时仍能采集，不为诊断唤醒进程或新拉 FGS。**autoEnabled 不参与诊断判断**；不新增设置项、开关、弹窗或提示，静默本地采集，不改变系统连接事实、不制造 Root 授权。
- 控制器只使用当前选择的 provider：先 probe，再 acquire 带 generation 的 lease；后台不得 openShell、请求授权、切换 provider 或启动 onboarding。

### 6.2 有界窗口与代次

每个采集窗口最多 3 个样本，目标时间点为 0s、3s、8s；实现与测试使用注入 scheduler/delay，不依赖真实睡眠。

- 同一时刻最多一个活动窗口；同一 MAC + 完整 CodecConfig + provider generation 在每进程最多完成一个窗口，连续播放回调及暂停后再播放均不得重复启动。
- MAC、provider generation 或完整当前 `CodecConfig` 变化可使旧窗口失效并允许唯一的新窗口；清空日志开启新诊断会话并允许重采。
- 配置变化信号只来自系统事件、既有 event-driven `readConfig` 与窗口自身样本；不得为发现变化新增周期性 `readConfig`。窗口内发现变化时先作废旧窗口，再按同一单飞规则处理。
- 每次窗口/清空/换机生成新代次。任何延迟、IPC 或超时返回后，提交前必须同时检查窗口代次、lease generation 和当前连接会话；旧结果只记一条受控摘要，不写入新证据。
- 暂停后可保留已完成样本；未完成的延迟采样不得继续跑到下一个播放会话。

### 6.3 特权采集接口

新增一个批量诊断 IPC 方法（建议名 `dumpRealtimeDiagnostics`），而不是让 App 串行发起三个无总预算的 binder 调用。返回结构化 JSON，每个来源独立：

- `bluetooth`：目标编码器的完整相关 State 段；无匹配时只附有限的段头/关键线索，不把其他编码器字段冒充目标。
- `audio`：与当前播放、输出设备、播放轨有关的片段。
- `audioFlinger`：与输出线程、混音线程、活动轨有关的片段。
- 每项分别包含 `status`（`ok / empty / timeout / error / truncated`）、有界 `content` 和脱敏后的错误摘要；一个来源失败不阻断其他来源。

服务侧必须流式过滤 stdout/stderr，先限制返回量再跨 binder；禁止先读整份 dump 再 waitFor。保留现有 `dumpBtState()` 给首页，不改变它的过滤与调用次数。

Root 诊断继续使用既有 READY anchor 与 IPC Mutex，不在本任务另开 Root 通道。首个诊断 IPC 超时后立即终止本窗口剩余样本，禁止继续排队重试；app 协程超时不能中断已阻塞的 binder transact，因此本设计与现有 `dumpBtState` 一样不能宣称消除底层冻结导致的 Mutex 占用，只能通过“一次失败即停”避免诊断自身放大阻塞。

### 6.4 独立诊断快照与导出

新增进程内、线程安全的 `PlaybackDiagnosticsStore`：

- 原始返回不得直接写入现有 200 行 LogBuffer；先经来源过滤、隐私清洗和大小限制。
- LogStore 只记录窗口开始、样本状态、截断/失败和完成摘要。
- Store 只保留最新有界窗口；清空日志同时清空 store 并使活动窗口失效。
- 0/3/8 秒样本在入库前压缩：相同字段只保留一次，变化合并为 `old → new` 与对应时间点；不得保存三份原文。现有机型、current、selectable 等已在其他诊断中存在的内容不重复。
- 优先保留现有解析器不认识的字段、采样率/输出链路线索和失败原因；相同行跨时间、跨来源只留一次并标注全部来源。
- 复制反馈日志时只取 store 快照，不发起任何新读取。

反馈报告仍最多 200 行，不另加 200 行附录：

- 无诊断时，既有 header + 最近 199 行普通日志的行为保持不变。
- 有诊断时，诊断附录最多 60 行，普通日志最多 139 行，加 1 行 header，总计仍不超过 200 行；附录另有独立字符上限。
- 普通日志和附录共用同一次设备别名发现与脱敏，确保 MAC/耳机名在全文稳定映射为同一 `deviceN`；超出预算必须显式保留 truncated，不得静默丢弃失败/截断状态。
- 复制本身始终无新增系统 I/O。

## 7. 隐私与性能约束

1. 仅采集文本诊断，不采集 PCM、媒体内容、HCI 包或完整 logcat。
2. 服务侧先按相关段/关键字段过滤，再限制行数与字节；音频 dump 中的包名、进程名、账户信息、MAC、设备名、路径等不得未经处理进入附录。
3. 在现有 `FeedbackLogSanitizer` 的设备别名之外，增加针对音频诊断的允许字段/段与专门清洗测试；只对已识别的 `name:` / `bdaddr=` 等格式做字段级处理，无法确认是否含设备名、包名或路径的行按“宁缺勿泄”丢弃，不以原始设备名留在附录为代价换取完整性，也不得用过宽正则误删采样率、codec 或错误证据。
4. 诊断只保存于进程内存；清空日志即删除，应用不新增持久化或网络权限。
5. 每个窗口最多 3 次批量采集；同一设备配置签名每进程最多一个窗口，暂停/换歌不重启。单样本和各来源都必须有有界超时与输出上限。
6. 不进入 `ApplyLock` 内执行新增 I/O，不阻塞自动/手动写入，不改变首页 3 秒轮询和 ListenerService 30 秒通知轮询。

## 8. 失败与状态解耦

- 本机连接、特权读取、每个 dump 来源、日志导出分别记录，不互相冒充。
- provider 未就绪：记录一次受控跳过，不自动授权、不把耳机改为未连接。
- `readConfig` 失败：保留本机已知连接，其他诊断源仍可采集；目标身份未知时不得猜段。
- 播放停止：已保存证据可导出，未完成窗口取消。
- 清空日志：已有与在途证据全部失效，迟到的旧任务不得复活。
- 样本为空/截断/超时：明确标识，不归类为“系统不支持实际传输”。

## 9. 验收要求

### 9.1 自动化（TDD）

1. 播放连续回调只启动一个窗口；0/3/8s 样本完成后自动停止，无第 4 次采集。
2. 同一设备配置签名每进程只完成一个窗口，暂停/换歌不重复；MAC、完整 CodecConfig、provider generation 变化正确作废旧窗口，清空后允许新会话重采。
3. 暂停、清空、断连后，迟到 IPC 结果不得写入；复制期间不发生 provider/dumpsys I/O。
4. 三类来源分别覆盖 ok、empty、timeout、error、truncated，一个失败不影响其他来源；首个 Root IPC 超时后不再启动剩余样本。
5. 大输出/慢进程不阻塞 binder 读线程，不超出返回与报告预算，截断状态不丢失。
6. 原始样本中的 MAC、设备名、包名、进程名和路径不得泄漏；采样率、codec、bitrate 与错误原因仍保留。
7. 三份原始样本按字段去重并合并变化，不重复保存已知配置；无诊断时普通报告保持 header + 199 行，有诊断时 139 + 60 + header 总计最多 200 行，别名跨普通日志/附录一致。
8. 现有 548 项测试不得通过放宽断言来适配；新增行为必须先 RED 后 GREEN，最终全量 JVM、lint、release 构建通过。

### 9.2 产品路径与外部验收

1. 用户只需保持音乐播放，不需新按钮；复制反馈日志的交互与等待不增加。
2. 清空日志、暂停后复制、断连重连、换 provider、无权限、无播放等路径均有明确结果。
3. 作者无目标真机，本地只能证明状态机、解析、脱敏与构建，不能宣称 Xiaomi/一加实际传输已支持。
4. 外部用户用同一候选版本播放后复制日志；下一轮必须能定位目标段/音频诊断是否存在及其原始形式，再决定是否新增解析或采样率展示。

## 10. 留给实现计划的具体决定

- AudioPlaybackCallback 与既有 isMusicActive 补充信号的最小去重接线位置。
- 三类 dump 的具体段过滤规则、每源字符/行数预算与总超时值，需以现有进程工具和隐私约束确定。
- Store 的普通报告/附录组合 API，需保持现有 `FeedbackLogSanitizer.sanitize()` 兼容测试。
- 新 IPC 方法在 Root/Shizuku fake 与 contract tests 中的统一接口名称和 JSON 字段。

## 11. Builder-check 裁决记录

1. **后台 fallback**：不新增 ticker/常驻轮询；AudioPlaybackCallback 缺失时只使用现有事件点，保留无法覆盖的 ROM 边界。
2. **Root IPC**：复用既有 anchor/Mutex，不扩大 RootTransport；首超时取消剩余样本，不能声称消除底层 binder 冻结。
3. **原始设备名隐私**：只允许字段级、已识别格式的清洗；不确定的原始行丢弃，不保留原文名称。
4. **配置变化来源**：不新增周期 readConfig，使用系统事件、既有事件读取和窗口样本。
5. **体积与频率**：按用户后续拍板改为同签名每进程一次、清空重采、字段去重、报告总量最多 200 行。
6. **静默且无新增开关**：用户明确裁决不加任何开关/弹窗/入口，autoEnabled 不参与诊断判断；只在进程已存活时按有界规则采集，绝不因此唤醒进程。
