## 协作协议

1. **分支隔离**：各自 `git worktree add` 独立工作区，分支命名 `fix/1.2.4-<topic>`，基于 master（`e0e0ee1`）。不得直接在主工作区/ master 上改。
2. **跨域改代码**：必须先 SendMessage 给 router 登记（文件、原因），router 裁决归属。
3. **共享文件**（strings.xml、SettingsRepository、build.gradle、版本号）：一律 router 在集成阶段统一改，worker 不碰。
4. **流程纪律**：systematic-debugging 四阶段；先根因报告再写修复；修复必须有 JVM 测试；完成前跑 `./gradlew testDebugUnitTest lint`（以仓库实际任务名为准）+ minified release 构建。
5. **汇报**：每个问题的根因结论、方案、完成证据都发 SendMessage 给 `stayhifi-58`；需要其他 worker 的信息也可直接互发（Worker2 = `Worker2`，worker3 = `worker3`）。
6. **不打 release 包、不改版本号、不碰 keystore。**

## Worker1 根因报告：问题 #1 与 #4（2026-11-06）

### #4 码率显示 "—"：根因已坐实（设计边界 + 文案误导）

链路：`MainActivity.kt:2027 quality = presentation.summary.quality` ← `CodecSummaryFormatter` ← `Masks.qualityLabel(family, cs1)` ← `HomeScreen.kt:360` 码率格 ← `:436 value ?: "—"`。

`qualityLabel` **仅 LDAC/LHDC 两族有解码**，SBC/AAC/aptX 全家/LC3/OPUS/UNKNOWN 恒返回 null → "—"。因此：
- aptX Adaptive（高通机常见）等编码器用户永远看到 "—"，从用户视角是"拉了满也没码率"，实为该编码器在 App 里无码率档位概念（`ManualSelection.qualityOptions` 对这些族本就为空）。
- 次因：LDAC/LHDC 的 cs1 出现未收录值时同样 null → "—"（无日志可查，需补诊断）。

工程修复（无需拍板）：quality 为 null 时记一条诊断日志（family + cs1 + source），供反馈日志取证。
产品决策（待用户拍板）：无档位编码器的码率格文案。

### #1 实际传输数据：数据源选项评估（收益-代价）

现状链路（`BtStateParser`）只认 dumpsys `A2DP <codec> State:` 段的 `transmission bitrate` 字段，**仅 vivo 栈实证可读**；ColorOS（一加 Ace 5 日志 A）段存在但值全空 `{}`，Xiaomi 15 Pro 无段。两样本已证 dumpsys 解析无可扩展空间。

| 选项 | 收益 | 代价 | 结论 |
|------|------|------|------|
| A. 产品口径优化：NO_DATA 时明说"该系统未开放传输码率回报"+引导反馈 | 诚实、零风险、当天可发 | 不解决核心诉求 | v1.2.4 必做（兜底） |
| B. 继续挖 dumpsys 其他段 | — | 已有两家反证，盲目性高 | 否决 |
| C. PCM 吞吐（framesWritten）冒充码率 | 看似有数 | 是 PCM 源端速率非编码后空中码率，显示即造假 | 否决（违反事实边界） |
| D. HCI snoop（btsnoop）解析 | **真实空中码率，全 codec 通用** | 需用户开开发者选项+root 读日志；隐私敏感须本地即时解析；工程量大（pcap 变体解析+L2CAP 通道跟踪） | 立 v1.3 研究项，先做可行性原型 |
| E. statsd 字节计数器 | 真实字节数 | 跨版本稳定性/shell 权限未验证 | 并入 D 的可行性研究一起查 |

产品决策（待用户拍板）：#1 的 v1.2.4 范围与 #4 的文案方向。
